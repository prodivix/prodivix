本文冻结 G4 跨 Provider、modality 与 tool 的生产控制平面。字段名表达 current domain 语义；数字版本只允许
出现在 wire schema、codec、migration、persistence 与外部 transport 边界。Provider invocation、多模态、托管能力
与真实模型评测由 ADR 66–69 分别拥有；后续实现不得绕过这组 contract 重新建立模型可直接写 Workspace、Agent
自我审批、无界工具调用或自报验证结果的第二条路径。

## 背景

G3 已建立 revision-bound Scenario、Impact、VerificationPlan、Evidence 与 Closure。Prodivix 因而能够判断一项
exact change 应验证什么、实际运行了什么，以及证据是否足以满足 Policy。G4 需要在这条链路上增加 Agent，
但 Agent 不是新的作者态 owner，也不是拥有特殊写权限的聊天窗口。

现有 LLM foundation 已提供 provider、streaming、context、tool 与 trace 的早期结构，但它仍有六个生产缺口：

1. task、run、取消、超时、恢复与强幂等没有统一 durable lifecycle；
2. 上下文未严格绑定 Workspace revision、Semantic Index、SourceTrace、敏感级别与来源可信度；
3. 模型输出到 Workspace write 之间缺少不可伪造的 proposal、approval 与 exact transaction binding；
4. provider、tool、权限、预算、网络、Secret、验证与审计没有形成同一个 fail-closed control plane；
5. 单一 OpenAI-compatible transport 不能证明 native protocol、provider operator 与 model-family portability。
6. 现代 Provider 的多模态、托管工具、状态/cache、后台 job 与 managed-agent 能力可能形成隐藏执行面。

把这些缺口留给 UI、prompt 或 provider adapter 会产生多条实际授权链，也无法证明失败时权限没有扩大。因此 G4
先冻结跨端 contract，再开始实现。

## 决策摘要

G4 使用下列唯一生产链：

```text
human intent
  -> immutable AgentTaskSpec
  -> revision-bound ContextPack
  -> bounded AgentRun + model/tool calls
  -> untrusted AgentActionProposal
  -> domain decode / validate / dry-run
  -> exact AgentProposalPreview + VerificationPlan
  -> explicit human AgentApprovalDecision
  -> domain Command / atomic Transaction
  -> Durable Outbox / Atomic Commit ACK
  -> committed VerificationPlan / G3 execution
  -> immutable Evidence / Closure
  -> terminal AgentRunOutcome
```

任何模型、provider、tool、UI、plugin、MCP server 或 Agent adapter 都不能跳过 proposal/approval 直接构造
`WorkspaceOperation`。生产写入只有一个 authority：现有领域 Command / Transaction 经 Durable Outbox 进入
Atomic Commit。

Provider-neutral 也必须可验证。exact Provider/model/capability qualification、媒体 representation、hosted tool
execution 与 release evaluation 分别遵循 ADR 66–69；无论由谁执行，最终都进入本 ADR 的同一 Task/Run、Grant、
Proposal、Approval、Commit、Verification 与 Audit 链。

## 1. 真相、projection 与 durable service state

### 1.1 Canonical Workspace

Workspace VFS 继续是作者态唯一真相。G4 新增一个 project-level typed document：

- `agent-policy`：保存可审阅的 Agent policy、能力边界、模型与数据策略、预算上限、审批规则和验证要求；
- 由 `core.agent` Command namespace 管理；
- 所有创建、编辑、删除和 policy adoption 都经过可逆 Command / Transaction；
- 不保存 credential value、prompt、model output、tool output、Run event、Evidence 或 provider runtime state。

`agent-policy` 可以引用由正式 Secret/environment/network policy owner 管理的 opaque reference，但不能保存解析后的值。

### 1.2 Derived projection

以下对象是 revision-bound、可重建或 content-addressed projection，不是 Workspace document：

- `AgentContextPack`；
- proposal dry-run 后的 candidate Workspace snapshot；
- semantic diff、impact、SourceTrace 与 risk projection；
- proposal preview；
- cost/usage summary；
- task/run timeline view。

projection 可以按 retention policy 缓存，但不能独立编辑，也不能在 Workspace undo/redo 后继续作为 current truth。

### 1.3 Durable Agent service state

`AgentTaskSpec`、`AgentRun`、model/tool invocation receipt、proposal、approval、commit receipt 与 audit event
由 `apps/backend` Agent service 持久化。它们记录对 exact Workspace truth 的操作历史，不是第二套作者态。

Agent service 必须：

- append-only 保存已发生的事实；状态由事件投影得到；
- 以 project/workspace/actor authorization 隔离；
- 使用 idempotency key、claim lease 与 generation fence；
- 支持刷新、进程重启和 worker loss 后恢复；
- 不把 service row materialize 成 Workspace 文档或 publication projection。

## 2. Owner 与依赖方向

### `@prodivix/ai`

唯一拥有 transport-neutral G4 current domain：

- `AgentPolicy`、`AgentTaskSpec`、`AgentRun` lifecycle；
- Context Pack manifest 与 grounding contract；
- capability grant、Task/Run budget、proposal/approval 与 audit event；
- 消费 ADR 66–69 的 provider/capability/media/tool/evaluation identities，不复制其 specialized semantics；
- `AgentActionProposal`、`AgentProposalPreview`、`AgentApprovalDecision`；
- Agent coordinator ports、state reducer、diagnostic taxonomy 与 canonical digest。

它不拥有具体领域 mutation、Workspace persistence、provider credential、browser transport、runner、Evidence store
或 React state。

### 各领域 owner

每个可由 Agent 提议的领域必须注册 stable `AgentActionDescriptor`：

- action type 与 current input；
- target/ref resolver；
- required read/propose/write capabilities；
- strict decoder、validator 与 dry-run planner；
- semantic diff、impact、risk、reverse Command 与 diagnostic contribution；
- policy/verification hints。

领域 owner 返回 Command 或原子 Transaction plan；`@prodivix/ai` 不解析 PIR、Route、Data、NodeGraph、
Animation、Code 或 Workspace 私有结构，也不把未知 JSON patch 当作 mutation。

### `@prodivix/workspace`

继续唯一拥有 Command、Transaction、History、Workspace validation、Durable Outbox input 与 Atomic Commit plan。
它不理解 prompt、model、tool 或 approval UI。

### `@prodivix/verification`

继续唯一拥有 Impact、Policy、Plan、Evidence 与 Closure 语义。G4 只能请求 planner、运行 canonical Plan 并引用
immutable Evidence/Closure digest，不能上传或生成自报 `passed`。

### application adapters

- `apps/backend`：Agent repository、claim/fence、authorization、secret callback、provider/network gateway、
  approval/commit orchestration 与 retention；
- `apps/web`：Task/Proposal/Approval/Trace 产品表面和 browser/local adapter；
- `apps/cli`：同一 current contract 的非交互 read/plan/propose/run adapter；不能增加隐式 `--yes` 写入后门；
- provider、MCP、local model、remote model 与 tool host 均位于 Adapter Ring。

## 3. AgentTask 与 AgentRun

### 3.1 AgentTaskSpec

Task 是人类创建的 immutable 请求。修改意图、scope、policy 或授权必须创建新的 task lineage，不能原地扩大。

```ts
type AgentTaskMode = 'explain' | 'plan' | 'propose' | 'apply';

type AgentTaskSpec = Readonly<{
  taskId: AgentTaskId;
  projectId: ProjectId;
  workspaceId: WorkspaceId;
  actor: PrincipalRef;
  mode: AgentTaskMode;
  baseRevision: WorkspaceRevisionVector;
  intent: BoundedText;
  intentDigest: CanonicalDigest;
  targetScope: AgentTargetScope;
  policyRef: AgentPolicyRef;
  policyDigest: CanonicalDigest;
  initialGrantRef: AgentCapabilityGrantRef;
  budget: AgentBudget;
  verificationRequirement: AgentVerificationRequirement;
  createdAt: Instant;
  idempotencyKey: IdempotencyKey;
}>;
```

约束：

- `intent` 有 byte/character 上限并经过 Secret scan；digest 使用 canonical bytes；
- `targetScope` 是 typed Workspace/semantic reference 集合，不接受文件 glob 或模型自造 target id；
- `baseRevision` 是 task 创建时的 exact revision，不允许 ambient “latest”；
- `apply` 只表示用户允许进入 proposal/approval 流程，不表示预先授权写入；
- explain/plan/propose 不得写 Workspace；apply 也必须等待 exact human approval。

### 3.2 AgentRun lifecycle

一个 Task 可以有多个 Run，但每个 Run 有独立 generation、budget ledger、Context Pack 与 trace。

```ts
type AgentRunPhase =
  | 'queued'
  | 'preparing'
  | 'running'
  | 'awaiting-approval'
  | 'committing'
  | 'verifying'
  | 'repairing'
  | 'cancelling'
  | 'terminal';

type AgentRunOutcome =
  | 'succeeded'
  | 'failed'
  | 'blocked'
  | 'cancelled'
  | 'budget-exhausted'
  | 'infrastructure-error';
```

稳定状态规则：

1. phase 是运行位置，outcome 只在 terminal 存在；不能以 `status: string` 混合二者。
2. `succeeded` 是 mode-specific：
   - explain：产生有来源的 bounded answer；
   - plan：产生有效 plan projection；
   - propose：产生可审阅但未应用的 exact proposal preview；
   - apply：Atomic Commit 已 ACK，且所需 G3 Closure 为 `satisfied`。
3. proposal 被拒绝、permission 缺失、revision stale 或 policy 禁止使用 `blocked`，不伪装成模型失败。
4. timeout 先触发 cancelling；只有所有 generation-owned callback 被 fencing，或 cleanup deadline 到达并记录
   infrastructure diagnostic 后，才进入 terminal。
5. retry 创建新的 attempt identity；已发生的失败、usage、cost、tool trace 与 proposal 不覆盖。

### 3.3 幂等与恢复

- Task create 以 actor/workspace/idempotency key 强幂等；
- Run start、tool call、proposal finalize、approval、commit、verification start 与 rollback 各有独立 idempotency key；
- active Run 由 lease holder 推进，所有 side effect 带 `runId + generation + callId`；
- late delta、late tool result、late commit ACK 和旧 worker callback 必须被 generation fence 拒绝；
- provider stream 断开后不从未知 token 边界“续写”；恢复时创建新 invocation，保留 parent lineage；
- 已完成的 proposal/approval/commit receipt 在重启后可重放 reducer，不重复执行 side effect；
- `localStorage` 只保存 panel/layout preference，不保存 Task、Run、grant、approval 或 pending write。

## 4. AgentPolicy 与 Capability Grant

### 4.1 AgentPolicy

Workspace `agent-policy` 表达项目作者可审阅的请求与上限，不是唯一 authorization authority。一次 Run 的
effective policy 是以下约束的最严格交集：

```text
platform/service enforcement
  ∩ organization/environment enforcement（若存在）
  ∩ project agent-policy
  ∩ actor authorization
  ∩ task/run capability grant
```

上游 enforcement policy 是 Agent service 的授权输入，不复制到 Workspace；manifest 记录其 immutable
digest/issuer/evaluation instant，不泄露私有规则正文。项目 Policy 或 Agent proposal 不能放宽上游约束。

```ts
type AgentPolicy = Readonly<{
  id: AgentPolicyId;
  name: string;
  providerRules: readonly AgentProviderRule[];
  modelRules: readonly AgentModelRule[];
  contextRules: AgentContextPolicy;
  capabilityRules: readonly AgentCapabilityRule[];
  approvalRules: readonly AgentApprovalRule[];
  networkRules: readonly AgentNetworkRule[];
  secretRules: readonly AgentSecretRule[];
  budgetCeiling: AgentBudget;
  verificationRules: AgentVerificationRules;
  retentionRules: AgentRetentionRules;
  privacy: AgentPrivacyPolicy;
}>;

type AgentPolicyEvaluation = Readonly<{
  projectPolicyRef: AgentPolicyRef;
  projectPolicyDigest: CanonicalDigest;
  enforcementPolicyDigests: readonly CanonicalDigest[];
  actorAuthorizationDigest: CanonicalDigest;
  effectivePolicyDigest: CanonicalDigest;
  evaluatedAt: Instant;
}>;
```

Policy 至少表达：

- ADR 66 exact provider/model/capability qualification allowlist 与 version/digest pinning；
- sensitivity class 到 provider、region、retention、training/telemetry eligibility 的映射；
- Context Pack item 类型、authority 与 maximum disclosure；
- read/execute/propose/write capability、target scope、tool allowlist 与风险级别；
- human approval、rollback 与 verification requirement；
- network destination/method/size/redirect/TLS policy；
- 允许解析的 Secret reference kind 与 callback purpose；
- per-invocation、per-run、per-task usage-vector/cost/time/tool/artifact 上限；
- trace、raw private artifact 与 audit retention。

Policy evaluation 必须绑定 exact project policy revision/digest、所有 enforcement digest、actor authorization
与显式 evaluation instant；不得读取未记录的 ambient feature flag 或在 Run 中自动放宽。下文 Grant、
Context、Invocation、Proposal、Approval、audit 中的 `policyDigest` 均指这次 evaluation 的
`effectivePolicyDigest`，同时可由 evaluation reference 追溯 project/enforcement inputs。

### 4.2 Capability Grant

Policy 是规则，Grant 是由 authorization boundary 签发的短期权限事实：

```ts
type AgentCapabilityGrant = Readonly<{
  grantId: AgentCapabilityGrantId;
  subject: PrincipalRef;
  taskId: AgentTaskId;
  runId?: AgentRunId;
  workspaceId: WorkspaceId;
  baseRevision: WorkspaceRevisionVector;
  targetScope: AgentTargetScope;
  capabilities: readonly AgentCapability[];
  toolIds: readonly AgentToolId[];
  runtimeZones: readonly RuntimeZone[];
  networkPolicyRef?: AgentNetworkPolicyRef;
  secretRefs: readonly SecretReference[];
  limits: AgentGrantLimits;
  policyRef: AgentPolicyRef;
  policyDigest: CanonicalDigest;
  issuedAt: Instant;
  expiresAt: Instant;
  maxUses: number;
}>;
```

Grant 约束：

- 只保存 Secret reference，不保存 value；
- capability 分为 read、execute、propose、approve、commit、rollback；模型永远不获得 approve/commit/rollback；
- 子调用的 grant 必须是父 grant 的严格交集，不能 union 或自动请求更宽 scope；
- 新 target、tool、network host、Secret purpose、transaction 或 revision 必须重新授权；
- 过期、revoked、use exhausted、policy drift、actor drift 或 revision drift 都 fail closed；
- grant 的签名/claim material 不进入 prompt、tool input、Workspace、trace 或 artifact。

## 5. AgentContextPack 与 grounding

Context Pack 是 content-addressed manifest，不是拼接字符串：

```ts
type AgentContextAuthority =
  'canonical' | 'derived' | 'user-provided' | 'external-untrusted';

type AgentContextItem = Readonly<{
  itemId: AgentContextItemId;
  kind: AgentContextItemKind;
  authority: AgentContextAuthority;
  source: AgentGroundingReference;
  revision: WorkspaceRevisionVector;
  contentDigest: CanonicalDigest;
  mediaType: string;
  byteLength: number;
  mediaRepresentationRef?: AgentMediaRepresentationRef;
  sensitivity: AgentSensitivity;
  instructionBoundary:
    'system' | 'developer-policy' | 'user-intent' | 'data-only';
  sourceTrace?: SourceTraceRef;
}>;

type AgentContextPack = Readonly<{
  contextPackId: AgentContextPackId;
  taskId: AgentTaskId;
  runId: AgentRunId;
  workspaceRevision: WorkspaceRevisionVector;
  semanticSnapshotRef: SemanticSnapshotRef;
  semanticProviderSetDigest: CanonicalDigest;
  items: readonly AgentContextItem[];
  omitted: readonly AgentContextOmission[];
  budget: AgentContextBudget;
  manifestDigest: CanonicalDigest;
}>;
```

构建规则：

1. 只从 Canonical Workspace、Workspace Semantic Index、Code Authoring、SourceTrace、Issues、Scenario、
   Verification Plan/Evidence 的公开 query 构建；禁止扫描 React store、DOM、editor private state 或 build cache。
2. 每个 item 必须可定位、可摘要验证，并记录被裁剪、拒绝或未知的原因。
3. 排序、去重、摘要与 digest 使用 canonical Unicode/code-point 与 JSON 规则，不能依赖 host locale。
4. `external-untrusted` 和工具返回内容始终是 `data-only`；其中出现的 “system prompt”、命令、审批或授权文本
   不获得 instruction authority。
5. prompt template 把 policy、human intent 与 data item 分隔，并在 output schema 中禁止模型回显 credential。
6. sensitivity 或 residency 不允许进入当前 provider 时，必须省略并产生 blocking diagnostic；不得降级成完整
   Workspace dump。
7. secret value、cookie、Authorization、private key、raw environment、signed URL 与 opaque capability 永不进入
   Context Pack。
8. 多模态 source/transform/omission/instruction semantics 由 ADR 67拥有；存在 `mediaType` 不等于自动获得对应
   capability qualification。

Context Pack 可重建不等于可以默默变化。一次 model invocation 绑定 exact manifest digest；Run 发现 revision 或
provider set drift 时，必须作废旧 proposal，并重新构建。

## 6. Specialized capability contracts 与 shared budget

本 ADR 只拥有跨能力的 Task/Run authorization 和 ledger 行为。专题语义的唯一来源为：

- ADR 66：Provider/model/capability qualification、invocation、reasoning/state/cache/job、usage vector；
- ADR 67：多模态 source/transform、媒体 Context、generated artifact candidate、realtime；
- ADR 68：hosted tool、retrieval/files/MCP、computer use、parallel/nested execution；
- ADR 69：real-model corpus、holdout、statistical repetition、grader/human review 与 release qualification。

`AgentTaskSpec.budget` 是 effective Policy ceiling 的等于或更小实例，组合 ADR 66 usage limits 与本 ADR 的
invocation/tool/repair/transaction/artifact/time/cost limits。ledger 由 coordinator 根据已接受 receipt 单调增加：

- 并发调用前原子 reserve，结束后 settle；
- crash 后未结 reservation 按 Policy 保守上界结算或人工 reconciliation；
- unknown usage 不能记零；
- 任一维度耗尽进入 `budget-exhausted`/`blocked`；
- 不自动切换未授权模型/capability、增加轮次、缩小 required evaluation 或丢弃已发生 usage/cost。

专题 adapter 只提供 descriptor/event/receipt，不重新拥有 Task、Grant、Proposal、Approval、Commit 或 Run success。

## 7. Tool contract

### 7.1 Tool 分类

```ts
type AgentToolEffect =
  'read' | 'ephemeral-execute' | 'proposal' | 'external-side-effect';
```

- read：查询 Workspace/Semantic/SourceTrace/Evidence 等公开 projection；
- ephemeral-execute：在 G2 bounded runtime 中执行，不写 Workspace；
- proposal：返回 typed action proposal，不应用；
- external-side-effect：默认不属于 G4；若只为验证所需，必须由现有授权 Runtime/Verification adapter 执行。

Agent tool registry **不得注册 model-callable Workspace apply、Atomic Commit、approval、rollback、Secret read-value
或 unrestricted network tool**。

### 7.2 生命周期

每个 tool call 经过：

```text
decode -> preflight -> authorize -> reserve budget -> execute
  -> normalize/redact -> stage -> finalize -> cleanup
```

稳定要求：

- input/output 都有 schema、byte/depth/item/time budget；
- call 绑定 task/run/generation/grant/context/tool registry digest；
- private runtime payload 只在 tool adapter callback 内可见；
- normalize 后只返回 bounded typed result、diagnostic、artifact reference 与 digest；
- cancel/timeout 后立即 revoke callback authority，late result 不得进入 context、proposal 或 evidence；
- cleanup 是 terminal acknowledgement；cleanup residual 形成 failure，不把 partial result 当成功；
- retry 使用新 call id，旧结果保留为审计事实；
- tool 自述 “permission granted”“tests passed” 或 “approval received” 没有 authority。

## 8. Proposal、dry-run 与 approval

### 8.1 模型输出

模型只能产生 `AgentActionProposal`：

```ts
type AgentActionProposal = Readonly<{
  proposalId: AgentProposalId;
  taskId: AgentTaskId;
  runId: AgentRunId;
  baseRevision: WorkspaceRevisionVector;
  contextPackDigest: CanonicalDigest;
  actions: readonly AgentProposedAction[];
  explanation: BoundedText;
  assumptions: readonly AgentAssumption[];
  requestedVerification: AgentVerificationRequest;
  modelInvocationRefs: readonly AgentInvocationId[];
  proposalDigest: CanonicalDigest;
}>;
```

每个 `AgentProposedAction` 只包含 stable owner、action type、schema identity、typed target 与 bounded wire input。
它不是 Command、Patch、Transaction 或 `WorkspaceOperation`。模型不得提交：

- generic JSON Patch / file overwrite；
- private editor store mutation；
- arbitrary shell/script 作为作者态修改；
- credential、approval assertion 或 fake Evidence；
- 未注册 owner/action type；
- code-owned 裸字符串替代 CodeArtifact/CodeReference。

### 8.2 Domain planning 与 dry-run

Coordinator 按 canonical action order 将 proposal 交给各领域 registry：

1. strict decode 与 unsafe key/path/size rejection；
2. target resolution、scope/capability/policy validation；
3. exact base revision 上的 domain dry-run；
4. 组合为一个可逆原子 Transaction；
5. materialize ephemeral proposed Workspace snapshot；
6. 计算 semantic diff、ImpactSet、risk、reverse plan 与 SourceTrace；
7. 由 G3 planner 生成 proposal target 对应的 `VerificationPlan`。

输出为 immutable `AgentProposalPreview`：

```ts
type AgentProposalPreview = Readonly<{
  previewId: AgentProposalPreviewId;
  proposalId: AgentProposalId;
  baseRevision: WorkspaceRevisionVector;
  proposedSnapshotDigest: CanonicalDigest;
  transactionDigest: CanonicalDigest;
  reverseTransactionDigest: CanonicalDigest;
  semanticDiffDigest: CanonicalDigest;
  impactSetRef: VerificationImpactSetRef;
  impactDigest: CanonicalDigest;
  verificationPlanRef: VerificationPlanRef;
  verificationPlanDigest: CanonicalDigest;
  requiredCapabilities: readonly AgentCapability[];
  risks: readonly AgentRisk[];
  diagnostics: readonly DiagnosticRef[];
  previewDigest: CanonicalDigest;
  expiresAt: Instant;
}>;
```

proposal target 是短期、只读、content-addressed projection，不占用或伪造 canonical revision。提交 ACK 后，
coordinator 必须针对 actual base/target revision 重新生成 committed Plan；required cells、impact、policy 或
transaction identity 若与审批预览不兼容，立即停止并要求新 proposal/approval，不能静默减弱验证。

### 8.3 Human approval

生产写入需要显式 `AgentApprovalDecision`：

```ts
type AgentApprovalDecision = Readonly<{
  decisionId: AgentApprovalDecisionId;
  decision: 'approved' | 'rejected';
  actor: PrincipalRef;
  taskId: AgentTaskId;
  runId: AgentRunId;
  previewId: AgentProposalPreviewId;
  previewDigest: CanonicalDigest;
  baseRevision: WorkspaceRevisionVector;
  transactionDigest: CanonicalDigest;
  impactDigest: CanonicalDigest;
  verificationPlanDigest: CanonicalDigest;
  grantRef: AgentCapabilityGrantRef;
  policyDigest: CanonicalDigest;
  rollbackAuthorization: 'none' | 'on-unsatisfied-closure';
  reason?: BoundedText;
  decidedAt: Instant;
  expiresAt: Instant;
}>;
```

approval 约束：

- actor 由 Auth boundary 解析，不能由模型/tool payload 指定；
- UI 必须展示 semantic diff、targets、risk、permissions、verification、cost-to-date 与 rollback policy；
- approval 绑定 exact preview，不存在可复用的 bearer “apply token”；
- 任一 digest、revision、grant、policy、actor authorization、expiry 或 proposal generation drift 都使 approval 失效；
- Agent/model/tool/plugin 不得作为 approver，也不得把自然语言 “用户同意” 解析为 approval；
- rejected decision append-only 保留；新 proposal 需要新 decision；
- CLI apply 也必须消费外部已签发的 exact decision，不提供跳过审批的通用 flag。

### 8.4 Commit

提交前 coordinator 再次执行 authorization、revision、policy、budget、approval 与 transaction digest preflight。
领域 owner 将已审批 plan 重新 materialize 为同 digest Command/Transaction；Workspace 经唯一
Durable Outbox / Atomic Commit 路径提交。

- 未收到 ACK 不得宣称已写入；
- ACK 丢失时按 operation/idempotency identity 查询，不盲目重发不同 transaction；
- 409/stale 不自动 rebase；创建新 proposal/preview/approval；
- History/undo 使用现有 reverse Command，不由 Agent 保存自定义 patch；
- 一次 proposal 最多产生 policy 允许的 transaction 数，默认一个原子 transaction。

## 9. Verification、repair 与 rollback

### 9.1 Verification binding

写入 ACK 后必须：

1. 保存 commit receipt 与 actual target revision；
2. 对 actual revision 重新生成 G3 Plan；
3. 验证它与审批的 proposal Plan compatibility，不能减少 required cells；
4. 通过 G3 adapter 执行；
5. 只引用 promoted immutable Evidence；
6. 由 Closure evaluator 在显式 instant 重算；
7. 将 Plan/Evidence/Closure digest 绑定到 Run。

`apply` Run 只有在 Closure `satisfied` 后才可 `succeeded`。`incomplete`、`unsatisfied`、`stale`、
`incompatible`、missing Evidence、unsupported required cell 或未知 trust 都不能被模型解释为成功。

### 9.2 Repair

失败可以触发 bounded repair round，但每轮都是新的：

```text
failed Closure
  -> grounded failure Context Pack
  -> new proposal
  -> new dry-run / Plan
  -> new human approval
  -> new transaction
  -> new Evidence / Closure
```

- 旧失败 Evidence append-only 保留；
- `maxRepairRounds`、token/cost/time/transaction budget 全部继续累计；
- Agent 不得反复重跑直到绿色，也不得修改 Policy、Scenario、baseline、exemption 或 required check 来制造通过；
- 若修复需要改变这些验证输入，它们是独立高风险 proposal，并按 policy 默认禁止同一 Run 自行提出；
- counterexample 与 regression 必须进入下一 Plan 的影响/required 集合，不作为 prompt 中的散文提示。

### 9.3 Rollback

Rollback 是 exact reverse Transaction，不是模型重新生成“恢复代码”：

- 只有 approval 明确授权 `on-unsatisfied-closure` 且 reverse digest、current revision、actor authorization
  仍兼容时，coordinator 才可自动提交；
- 有后续人类/Agent change、reverse validation drift、external side effect 或 authority drift 时停止并等待人工处理；
- rollback 本身产生新的 Workspace revision、History/Outbox/ACK 与 Verification Plan；
- rollback failure 不删除原 change、Evidence 或 audit trail。

## 10. Audit、trace 与 retention

### 10.1 Stable event families

Agent audit log 是 bounded append-only event stream，至少包含：

- `task.created` / `run.started` / `run.phase-changed` / `run.terminal`；
- `context.built` / `context.omitted` / `context.rejected`；
- `model.started` / `model.completed` / `model.failed`；
- `tool.authorized` / `tool.started` / `tool.completed` / `tool.cancelled` / `tool.rejected`；
- `proposal.received` / `proposal.rejected` / `proposal.previewed` / `proposal.stale`；
- `approval.requested` / `approval.decided` / `approval.invalidated`；
- `commit.started` / `commit.acknowledged` / `commit.conflicted`；
- `verification.started` / `verification.closed`；
- `repair.started` / `rollback.started` / `rollback.acknowledged`；
- `budget.reserved` / `budget.settled` / `budget.exhausted`；
- `security.policy-denied`。

每个 event 记录 event id、task/run/generation、actor/producer、timestamp、previous event digest、payload digest、
policy/grant identity 和 bounded sanitized payload。跨分区持久化使用 sequence/fence 防止重排；hash chain 用于
检测缺失或篡改，不替代数据库 authorization。

### 10.2 不进入普通 trace 的内容

默认 trace 不保存：

- raw system/developer prompt；
- 完整 Workspace/context bytes；
- model reasoning/private chain-of-thought；
- Secret、credential、cookie、signed URL、capability token；
- unrestricted raw tool output、DOM、network body、environment 或 terminal stream。

如受控调试需要 raw prompt/model/tool artifact，它只能进入独立 encrypted、short-retention、role-restricted
artifact store；manifest 只记录 digest、size、media type、redaction class 与授权 reference。无论何种调试级别，
Secret value 都不得持久化。

ADR 66允许的 opaque continuation 只保存在独立 encrypted callback store，以 reference/digest 进入受限 receipt；
它不属于普通 trace，也不能被展示、索引或解释为 reasoning evidence。

## 11. Security 与 fail-closed matrix

| 风险                               | 必须行为                                                                                 |
| ---------------------------------- | ---------------------------------------------------------------------------------------- |
| prompt injection                   | external/tool content 固定为 data-only；尝试改变 policy/approval/tool scope 时拒绝       |
| untrusted structured output        | strict schema + owner registry + bounded value；未知字段/owner/action fail closed        |
| target/scope escalation            | grant intersection + exact target resolution；需要新的人类授权                           |
| self approval                      | actor-bound approval service；模型/tool 文本永远不构成 decision                          |
| Secret exfiltration                | callback-bound resolver；value 不进入 context/model/tool trace/artifact                  |
| network escalation                 | 独立 network grant、allowlist、redirect/DNS/IP revalidation、size/time budget            |
| model/provider protocol drift      | adapter/operator/endpoint/model identity 或 policy mismatch 使 invocation/proposal 无效  |
| provider diversity laundering      | 同协议换模型、aggregator alias 或重复 model lineage 使 evaluation manifest invalid       |
| hidden provider-side state         | 默认 stateless；未授权 parent state/storage/retention 使 invocation 与 evidence 无效     |
| cross-modal injection              | media/OCR/transcript/metadata 固定 data-only；不能改变 policy/grant/approval             |
| hidden Provider-hosted execution   | 无 exact descriptor/call receipt 即拒绝；opaque managed agent 无 apply authority         |
| computer-use authoring             | 不能按坐标改 Workspace；必须回到 typed proposal/approval/Transaction                     |
| revision drift                     | proposal/approval stale；不自动 rebase 或套用旧 diff                                     |
| tool cancellation race             | generation fence + revoked callback authority + cleanup acknowledgement                  |
| fake tests/evidence                | 只接受 G3 promoted Evidence 与 Closure digest                                            |
| retry-to-green                     | attempt lineage、失败保留、bounded retry、Policy 决定 unstable                           |
| prototype pollution/path traversal | shared safety primitive、strict typed path、无 caller-controlled plain-object assignment |
| cost runaway                       | atomic reserve/settle ledger；任何上限耗尽即停止                                         |

生产 apply-capable Run 不允许浏览器直接持有 provider API key。Secret 只可由授权的 server/native adapter 在
callback-bound transport 内解析；Local mock、完全本地模型或 read-only explain 可以有单独 adapter，但不得因此获得
Workspace commit 权限。

## 12. Product contract

G4 产品面至少包含：

- Task composer：mode、target、policy、budget 与 intended verification；
- Run timeline：当前 phase、cancel、budget、model/tool identities 与 recoverability；
- Context inspector：来源、authority、revision、sensitivity、omission，不默认展示敏感正文；
- Proposal review：semantic diff、Impact、Plan、risk、permissions、cost 与 rollback；
- approval/rejection：可访问、不可被 prompt/UI overlay 混淆的独立确认面；
- Verification/repair：复用 G3 Plan/Evidence/Closure，不复制绿色状态；
- audit export：bounded sanitized manifest，可验证 event/digest 链；
- stale/blocked/security state 的明确诊断与人工下一步。

产品不得：

- 仅显示自然语言总结而隐藏 exact diff/Plan；
- 把 streaming 文本当作已执行动作；
- 用 spinner 掩盖 awaiting approval、cancel cleanup 或 recovery；
- 在 approval dialog 中默认勾选扩大权限、自动 repair 或 rollback；
- 将 provider/model 高级设置常驻在零技术路径；默认由 Policy 选择，只有 policy/diagnostic 需要时展开。

## 13. G4 与 G5/G6 边界

G4 关闭单一项目、单一授权人对 Agent change 的可信闭环。以下不属于 G4：

- organization role hierarchy、多人 review quorum、merge queue、release/deploy approval；
- presence、comment、branch collaboration 与 cross-device change review；
- production telemetry 自动触发 repair/deploy；
- public Agent/Tool marketplace、第三方 publisher trust、billing/revenue sharing；
- Agent-to-Agent delegation、跨 organization identity federation；
- opaque Provider-managed agent 的 production delegation、任意动态 MCP marketplace 与跨项目 ambient memory；
- 无人值守 production mutation。

这些能力分别属于 G5/G6，不能以提前加入通用 `reviewers: string[]`、任意 MCP 权限或长期 bearer grant 的方式
污染 G4 contract。

## 14. 拒绝的方案

### 模型直接调用 apply tool

拒绝。它把 prompt/tool output 变成 write authority，绕过领域 planner、人类 approval 与 Atomic Commit preflight。

### 通用 JSON Patch 或文件覆盖

拒绝。它无法稳定表达领域不变量、reverse Command、semantic impact、CodeArtifact owner 与 migration。

### 可复用 apply token

拒绝。bearer token 不能充分绑定 actor、policy、Plan、impact、transaction 与 revision。G4 使用 append-only exact
`AgentApprovalDecision`。

### 把 Task/Run/trace 写进 Workspace

拒绝。它会让运行事实参与 authoring revision/undo，并产生第二套服务状态镜像。

### 完整 Workspace dump 作为 prompt

拒绝。它不可扩展、无法解释来源和裁剪，也扩大 Secret、privacy 与 prompt injection 面。

### Agent 自报测试通过

拒绝。只有 G3 planner、promoted Evidence 与 Closure 有验证 authority。

### 用单个真实模型 smoke 证明 Agent 质量

拒绝。smoke 只能证明 adapter/stream/schema 基本可用，无法证明长上下文 grounding、跨领域 proposal、
repair、adversarial robustness 或随机稳定性。G4 Exit 必须消费 version-bound corpus/repetition/threshold
完整的 `AgentModelEvaluationManifest`；具体 statistical floor 见 ADR 69。

### 把同协议模型或 aggregator endpoint 计作多 Provider

拒绝。同一 OpenAI-compatible adapter 下换模型只增加 model configuration，不增加 native protocol diversity；
aggregator 转发也不能证明独立的 provider operator、模型家族或原生协议行为。G4 closure 分别验证 protocol、
operator 与 model-family-owner diversity；具体 qualification 单位见 ADR 66/69。

### 自动 rebase、自动放宽预算或自动扩大权限

拒绝。它会使人类审批不再绑定 exact change，并在失败时扩大能力。

### 自动重跑或改 baseline 直到绿色

拒绝。它隐藏失败与 flaky，破坏 Evidence lineage。

## 15. Contract freeze 与变更规则

以下内容已在 G4 实现开始前冻结：

1. owner 与唯一 Workspace write path；
2. `agent-policy` 是唯一 G4 Workspace document，Task/Run/trace 不属于 Workspace；
3. Task mode、Run phase/outcome 分离；
4. Context Pack authority/instruction boundary 与 revision/digest binding；
5. ADR 66–68 的 exact model/provider/capability/media/tool/policy/grant/usage identity；
6. model 只产生 proposal，领域 owner 产生 Command/Transaction；
7. human approval 绑定 exact preview/transaction/Impact/Plan/revision；
8. apply success 必须有 Atomic Commit ACK 与 G3 satisfied Closure；
9. repair 每轮重新 proposal/approval，rollback 使用 exact reverse Transaction；
10. Secret/network/prompt injection/permission escalation fail closed；
11. append-only audit 与 recovery/idempotency/fencing；
12. ADR 69 的 native Provider/profile diversity、corpus/holdout、risk-stratified repetition、metrics、budget、
    human review 与 expiry contract；
13. G4 与 G5/G6 的产品边界。

若实现发现需要改变上述语义，必须先新增 ADR 或明确修订本文，更新 milestone/evidence，再改代码。只增加 wire
version、migration、adapter 私有字段或不改变 current domain 的内部优化不解除 freeze。
